# artifactd RSS investigation — 2026-10-05

## Finding

Subsequent source-matched optimized ARM Massif profiling identified growing
redb LRU queue metadata: 2,155,008 guest bytes in `VecDeque<u64>::grow` after
5,000 full blob cycles. Reused page offsets allow old queue tokens to alias
newly cached entries. The exact upstream generation-tag repair has been
backported, with pre-fix failing and post-fix passing owner regressions.
[Current attribution and provenance](RSS_CURRENT_RELEASE_20261005.md)
supersede the earlier unresolved-owner assessment below. Native memory
qualification for the repaired release remains open; the historical RSS
samples and failed recorder attempts retain their original limits.

The x86 sample is especially diagnostic: while the private redb file remained 3,538,944 bytes, one-thread daemon RSS rose from 6,692 KiB at iteration 0 to 56,636 KiB at iteration 60,000. A contemporaneous read-only `/proc/<pid>/smaps_rollup` sample (PID 2373758, same run) reported 63,032 KiB RSS, 59,860 KiB anonymous RSS, and 57,344 KiB `AnonHugePages`. Thus most of the resident growth was private anonymous memory, and about 56 MiB was huge-page-backed. The mismatch between the runner checkpoint and smaps sample reflects that the process advanced while the two reads were taken; neither is an exact same-instant pair.

The ARM64 run shows the same growth without transparent huge pages. Before its intentional restart, the first blob phase had reached 90,000 with 78,588 KiB RSS and a 3,538,944-byte state file. After restart, the daemon began the OCI phase at 8,240 KiB; at OCI iteration 6,000 it reported 14,472 KiB RSS. A read-only sample at that point reported 15,396 KiB RSS, 10,448 KiB anonymous RSS, and zero `AnonHugePages`. This restart drops process-local growth back near baseline, but does not distinguish leaked live objects from allocator-retained pages. Growth then recurs under a different request mix.

Both hosts report one daemon thread and roughly 13–14 FDs, so thread, socket, or descriptor accumulation is not supported by these checkpoints. State size reaches 3.5 MiB by blob iteration 10,000 and remains there; the operation journal explicitly retains at most 4,096 operations. These observations argue against a growing journal or persistent redb dataset as the source of the additional tens of MiB.

## Source and dependency evidence

- `src/api/mod.rs:61-72,75-97` runs a serial accept/handle loop. Request bytes, the deserialized `Request`, dispatch results, and response bytes are locals of `handle`; there is no request queue or worker pool retaining completed requests. `src/api/intake.rs:12-30` preallocates a fixed 32 pending-connection slots, while the campaign observes one thread and no rising FD count.
- The blob import path in `src/cas/import.rs:162-188` streams through one fixed 64 KiB buffer. It does not retain a blob-sized payload in memory. Import metadata and dispatch state are scoped to a single synchronous call.
- `src/state/redb.rs:48-74` retains the database, root directory capability, and health flag in `State`. Redb 4.3.0 is configured with an 8 MiB page-cache budget (`src/state/redb.rs:66-69`); its `PagedCachedFile` implementation enforces the configured combined read/write cache ceiling (`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/redb-4.3.0/src/tree_store/page_store/cached_file.rs:287-293`). This makes unbounded redb page-cache growth an unlikely explanation, though it does not bound allocations in Rust's or libc's allocator around each transaction.
- `src/api/journal.rs:11,45-52` enforces a 4,096-entry operation window and validates the persistent inventory against that bound. The measured state file plateau is consistent with this contract.
- API request/response parsing and redb transaction work allocate temporary objects on every call. They are dropped at call/transaction completion in the inspected path. Their allocation traffic can grow with operations even when live application state is bounded; the current RSS-only measurements cannot tell whether freed pages return to the OS.

## Assessment

1. **Possible: allocator retention/fragmentation, with x86 THP magnifying RSS.** The steep anonymous-RSS growth, large x86 `AnonHugePages`, return to baseline after process restart, and repeated growth after restart fit a heap whose freed pages remain resident. This is consistent with, but does not prove, the hypothesis. ARM64's lack of THP and continued RSS growth show THP is an amplifier on x86, not a complete explanation. The newer subset profile does not show a flat live heap, so it does not establish this explanation.
2. **Still possible: a live allocation retained below the inspected source boundary.** The daemon invokes redb and serde internals repeatedly; RSS alone cannot rule out retained allocator objects or a dependency leak. No owned collection in the inspected API loop grows by completed request count, and the configured redb data-page cache is bounded.
3. **Unlikely from current evidence: journal/database payload growth, large blob buffers, threads, or FDs.** State bytes plateau, journal retention is bounded, the import buffer is 64 KiB, and resource counts stay flat.

No allocator tweak or production-source instrumentation is justified by this evidence. The current campaign remains unqualified for bounded RSS.

## Controlled profiler calibration and resource limit

On the isolated persistent x86 runner (`tihan-apollo`), I provisioned heaptrack 1.5.0 into a private directory without changing global packages, then copied the exact qualification daemon and `api_churn` executables there (SHA-256 `f90c45c6af42df402749b883526f9f557236cd763815b5ea025255dbc2c1eff5` and `9b4178ef03b3e17cdd438ce39f0041acd556727df5c842af708064f4011fa442`, respectively). The first wrapper instrumented only the runner process; I detected that the child daemon had no heaptrack mapping, stopped only that isolated child, and discarded the invalid profile. A corrected private wrapper executed the daemon itself with heaptrack's preload. `/proc/<daemon-pid>/maps` confirmed the preload on the actual daemon during the successful 100-cycle calibration.

That calibration recorded 1,008,176 allocation events, 1.26 MiB peak allocated heap, and 450.24 KiB live at process `SIGKILL`; peak RSS including profiler overhead was 11.06 MiB. `api_churn` terminates its child with `SIGKILL`, so the end-live number is an upper bound that includes allocations whose destructors could not run. This short calibration neither measures the sustained churn interval nor establishes a leak. The release executable is stripped, leaving retained stack addresses unsymbolized.

An initial 2,500-cycle attempt could not start because creating its isolated store failed with `ENOSPC` while the runner had 648 MiB root headroom. After the owner reclaimed stopped build intermediates, a fresh read-only check showed 6.8 GiB available; the same bounded direct-daemon profile then completed successfully. The campaign processed 2,500 blob cycles in 112.33 seconds, with no OCI cycles. Heaptrack recorded 46,609,254 allocation calls, 4.55 MiB peak heap, and 14.61 MiB peak RSS including profiler overhead. At the runner's intentional `SIGKILL` restart, heaptrack classified 3.64 MiB as outstanding: the largest retained stack accounted for 2.37 MiB across 2,393 calls, followed by 323.58 KiB across 344 calls and 221.18 KiB across 202 calls. These are process-end live allocations, not proven leaks, because the runner kills the daemon without running destructors. The final-inventory check passed; the operation table held 4,061 entries and the state file was 3,538,944 bytes. The clean post-restart daemon's profile contained 38 KiB of data.

Heaptrack confirmed instrumentation on the actual child daemon, but the exact release executable has no debug symbols. No matching separate debug file was present in the standard build-id locations or the already-existing remote release target. Thus the retained stacks remain address-only, and I did not rebuild or duplicate a Cargo target to symbolize them. The top 2.37 MiB site begins at `0x55cf4babc039`, followed by `0x55cf4bac1912`, `0x55cf4babde42`, and `0x55cf4b98ec39`; these are ASLR runtime PCs from this process only. The heaptrack profile itself is retained in the private runner directory. Do not reclaim unrelated runner files or mutate active qualification targets. This single 2,500-cycle run identifies no source-level owner and is insufficient to distinguish bounded live state/cache from a per-request leak; a longer profile with usable matching symbols or an in-process checkpoint comparison remains necessary before proposing a fix.

## ARM64 exact-symbol profile and recorder limits

On the isolated ARM64 runner, I copied the existing native debug daemon (SHA-256 `8f6cabd652683ad8adac63c8cbc119ec6884a2095ac0df4966aea2df35c61b77`, Build ID `3806e2f8b7a70d723833cd04bd86715d2ec9aa32`) and used the existing qualification churn harness. Heaptrack 1.5.0 was downloaded and extracted privately; no system package state or production source was changed. `/proc/<daemon-pid>/maps` confirmed the preload was present in the actual daemon child.

The 2,500-blob run completed in 109.88 seconds; the 10,000-blob run completed in 505.36 seconds. Both had zero OCI operations, final state size 3,538,944 bytes, clean inventory/status checks, and bounded operation counts of 4,061 and 4,081. During the 10,000 run, daemon RSS rose from about 13.8 MiB to 21.9 MiB, PSS was 19.4 MiB, private dirty was 9.8 MiB, `AnonHugePages` remained zero, and state size stayed flat. This is direct RSS evidence for the exact ARM debug build and workload only.

The allocation recorder did not provide usable attribution. Its 10,000-cycle `heaptrack_print` summary claimed 567.02 MiB peak and 566.47 MiB end-live; the 2,500-cycle summary claimed 4.64 MiB peak and 3.82 MiB end-live. The 10,000 profile also produced malformed/interleaved-record warnings, so those allocation totals are not credible and must not be compared or assigned to an owner. The interpreter output contains allocation records with trace index `0` (for example `a 12000 0`), even though the executable retains DWARF and a symbol table. The failure is upstream of symbolization; it does not demonstrate a live allocation leak.

I inspected the exact Ubuntu source package for heaptrack 1.5.0+dfsg1-2ubuntu3, with the source archive checksums matching its `.dsc`. Its `LineWriter` buffers to `PIPE_BUF` and flushes each buffer with one `write`; `HeapTrack::op` serializes tracked operations with a process-wide mutex; fork handlers suppress tracing in forked children. This source review does not support a thread-interleaving explanation by itself. The preload dynamically depends on ARM64 `libunwind.so.8`, and the recorder calls `Trace::fill(2)` for malloc/realloc, dropping its first two frames and emitting an empty trace when the unwind depth is no greater than two. Insufficient/unavailable unwind frames are therefore a plausible reason for zero trace indexes; the available evidence does not distinguish that from corruption or truncation in the captured event stream. The wrapper retained interpreted output rather than the raw FIFO stream, so the malformed-record warnings cannot be localized between producer, FIFO capture, and interpreter. No further high-volume heaptrack run is justified until a short isolated recorder fixture validates nonzero stack traces and a well-formed event stream, or a different maintained profiler is used. No source owner or allocator change is justified from these profiles.

## ARM heaptrack diagnostic and Massif follow-up

A privately provisioned ARM64 heaptrack 1.5.0 probe isolated the empty-stack recording failure. A retained 4 MiB allocation through the exact preload produced two allocation records but no raw `t` stack-frame records in the FIFO; the interpreter therefore was not responsible for dropping frame data. The hook's `Trace::fill(2)` removes two leading frames. An `unw_backtrace` interposer observed only three frames, all within the tracing hook, so this skip leaves no caller frame to record. This is consistent with an unwind failure around the AArch64 PAC-enabled hook CFI, but does not prove that PAC/CFI is the sole upstream cause. Heaptrack's allocation counts and live-byte totals from the larger churn profiles remain invalid for attribution.

I also extracted Valgrind 3.22/Massif privately, without changing system packages. On the same 4 MiB C probe, Massif produced source-symbolized peak snapshots naming `make_retained_allocation` and `main`, validating the profiler and symbols in this environment. A 100-cycle real-daemon attempt used the exact debug daemon and passed its workload/final-inventory checks, but the existing churn harness sends `SIGKILL` to its child at restart/exit; Massif wrote no profile file. That run therefore supplies no allocation-owner evidence. A cleanly terminating daemon Massif run remains unverified because the ARM runner stopped accepting SSH connections during this follow-up. I did not repeat the workload, alter the production daemon, or infer an owner from the failed recording.
